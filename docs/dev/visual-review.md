# 界面目检机制（交接关 + 发版关）

> 2026-11-05 与用户议定。背景：连续六波反馈、十余轮返工的机制性根因，是交付门禁里从来没有「渲染出来看一眼」这一环——五个 E2E 门禁脚本（check-pages / check-wizard / check-toggle / check-edit-rules / check-dark-mode）全部只断言 DOM 与样式属性，无一截图调用；commit 正文与 HANDOFF 多处明写「视觉效果留给用户人工验证」，用户被流程安排成了唯一目检环节。本文件把这一环补上，同时用范围闸门防滥用（用户 token 有限，审查成本必须可控）。

## 两条关

### 交接关（每轮交付）

- **范围**：只拍本轮改到的界面，通常 2~5 张；不做全量。
- **流程**：构建产物 → 真实浏览器截图 → 派「新眼睛」（见下）审**一轮** → 截图与问题清单随交付给用户 → 用户确认后再装机。不再出现「装完才发现」。
- **免审**：纯文案改动（只动 i18n 文字、不动布局与控件）不派审查，只把截图贴给用户。
- **每轮只审一轮**：审查员一次出完问题清单，不许多轮往返挑刺。

### 发版关（每版一次）

- **全量**：弹窗、设置页、向导各步、页面内组件（收放钮、面板）、暗色模式，全部真实渲染截图。
- **标准（两档合一）**：
  - 无障碍硬伤逐条对照 [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 全查、零容忍：对比度、点击区 ≥ 24×24、焦点可见、错误可识别；
  - 其余按「一个正常人打开扫一眼，提不出刺眼毛病」验收。
- **不做**逐条对照设计规范全文的吹毛求疵式检查——那档 token 翻几倍，拦的多是没人会注意的问题。

## 审查员（「新眼睛」）

- 用子代理，**只看截图、不看代码**，flash 档模型。
- 无代码上下文是**有意为之**：审查员和用户处境相同（对界面没有先入之见），才看得见用户看得见的问题。写代码的眼睛有「我写的肯定对」的包袱，已被证明是盲区来源。
- 审查依据：`docs/dev/consistency-checklist.md` + AGENTS.md「界面整屏审查」五条 + WCAG 硬伤清单。
- 输出格式：每张截图一份问题列表（位置 + 问题 + 违反哪条权威条款）；没问题的截图明确写「无」。

## 挑出的问题怎么处理

- **一致性 / 清晰度缺陷**（两处长得不一样、叫法分裂、图标看不懂）：当场修完再交付，不问用户。
- **产品取舍**（布局重排、流程改动、删功能）：列成选项、带推荐，问用户——不拿「审查发现了」当免问牌，也不攒着一堆小问题去问。

## 修一类的留痕（轻量版）

- 修文案 / 控件类问题时，回复末尾补一行：「同类位置扫过 X、Y、Z，其余无同类」。
- 不建大清单、不上硬流程。漏一处的代价是一整轮返工（#74 在立规后仍漏四处，实证），比这一行字贵两个量级。

## 防滥用闸门（token 纪律）

1. 只拍改到的界面；
2. 每轮只审一轮；
3. 纯文案免审；
4. 发版全量一版一次；
5. 审查员永远用 flash 档，不用旗舰模型（教训：旗舰模型全程视觉验证会把总额度快速烧穿）。

额度紧张的时期回到纯节俭档（可只保发版关）；额度富裕时可加深为额外全量巡检。**两条关里，发版关优先级永远高于交接关。**

## 一致性复查清单

见 `docs/dev/consistency-checklist.md`。性质：**只是索引，不是权威**——每条必须挂靠权威来源（docs/GLOSSARY.md、docs/design-ui.md、WCAG 条款），与权威冲突时以权威为准。用户推翻某个判断时，同一提交里改权威文件、删条目、全项目扫一遍旧样式 / 旧叫法。
