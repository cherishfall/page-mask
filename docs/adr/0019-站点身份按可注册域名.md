# 站点身份：一个网站 = 一个可注册域名

日期：2026-11-11 · 状态：已采纳 · 相关：issue#162、ADR-0004（本地存储与导出导入）、`core/site-key.ts`、`core/site-grant.ts`

## 背景

旧版把「站点身份」定义成含协议与非默认端口的 origin：`https://weibo.com` 与 `https://s.weibo.com` 是两份配置、两次授权、管理页两行。用户认知里它们是同一个网站——在 weibo.com 收起的侧栏，到 s.weibo.com 又要重设一遍；同一品牌在列表里出现多行，还会影响「全部允许访问」与导入时的归并。

Chrome 的权限、动态注册、存储 key 又都按 match pattern / 字符串组织，站点身份一旦改变，会同时牵动存储、权限申请、对账、迁移与导出导入。#162 因此分成两步：先换内核（第一阶段，`b32fa39`），再补界面提示与文档（本阶段）。

## 决定

1. **站点身份 = 可注册域名（eTLD+1）**，忽略协议与非默认端口：`weibo.com` / `www.weibo.com` / `s.weibo.com` 是同一个网站；`weibo.com` 与 `weibo.cn` 仍是两个。规范形态是小写、punycode、不带协议与路径的 key（如 `weibo.com`）。
2. **例外按原样保留**：IP 字面量、`localhost`、单标签主机名、带非默认端口的地址保留 `host[:port]`，不合并子域。本地开发服务与内网地址不该被并进某个公网站点；单标签主机名本身没有 eTLD+1；端口是保守边界（`weibo.com:8443` 与 `weibo.com` 视为两个站点）。
3. **权限按站点申请**：普通域名一次申请「裸域 + 子域」两条模式（`*://weibo.com/*`、`*://*.weibo.com/*`）；IP / localhost / 单标签只有一条精确模式；带端口的站点用 `http://host:port/*` 与 `https://host:port/*` 两条——Chrome 不接受 `*://host:port/*`（整批 `Invalid port`，权限反而收不回），协议又不参与站点身份，所以拆成两条。
4. **生效范围仍按页面实际 URL 判定**：合并站点不等于合并范围。「只在 weibo.com 首页收起」不会套到 s.weibo.com；规则的 scope 匹配继续走 `core/origin.ts` 的页面来源与路径，和站点 key 是两件事。
5. **存储 key = `profile:<站点 key>`**；旧版 `profile:https://…` 键在读时懒迁移：按站点归并、字段取舍复用 `mergeProfiles`、先写后删、幂等。没有新增 `onInstalled.update` 分支。
6. **迁移用户的旧精确授权继续有效**：手里只有 `https://weibo.com/*` 这类模式的站点仍算已授权，不会因为新代码期望通配模式而全员变成「待授权」。但旧模式只覆盖它写明的页面——打开 s.weibo.com 时弹窗会提示「这个页面还没允许访问」，点「允许访问」补上两条模式。

## Considered Options

- **维持 per-origin 精确身份**：否决。同站子域各配一遍与「零专业知识」的产品定位相悖；用户报障的场景正是「在 weibo.com 设过，s.weibo.com 没生效」。管理页、导入导出、胶囊与弹窗都要继续把同品牌拆成多个网站。
- **给用户「精确 / 宽松」开关**：否决。项目不加选项（核心原则：不要求用户先学会概念）；两种身份模型会渗透到存储 key、权限、迁移、导入与全部比较点，维护成本翻倍，而绝大多数用户只需要一种。
- **完整内置 PSL**：否决。完整列表体积、更新节奏与维护责任都不适合放进扩展；内置常见子集已覆盖绝大多数用户会遇到的站点，长尾的代价只是「同后缀两个站点被当成一个」，不丢数据。
- **按 host（含子域）精确身份**：否决。换一个子域就丢配置，等于把 per-origin 的问题换一种写法。

## Consequences

- **子域合并的预期与代价**：同一注册域下的页面共用一份配置、一次授权、列表一行。代价是本来可以独立配置的两个子域（例如同一公司的两个业务子域）会被合并；由于规则仍按页面 URL 生效，合并后不会把规则套到不该生效的页面，只是清单与授权范围合并了。
- **权限要两条模式**：一次「允许访问」会授予裸域与子域两条；删除站点时两条一起收回。旧用户手里可能只有一条精确模式，功能不受影响，未覆盖的页面由弹窗提示补授权。
- **旧配置懒迁移**：旧 key 在第一次读存储时按站点键归并（管理页、弹窗、后台读配置都会触发）。迁移是幂等的、先写后删；迁移后同一站点只剩一条配置。导出文件 `formatVersion` 仍是 1，旧文件里的 origin 在读取时归一。
- **迁移用户沿用旧精确模式不会丢授权**：这也是「不主动扩权」的取舍——不替用户补授他没点过「允许」的子域；需要时由弹窗上的一句话与一次点击完成。
- **PSL 只内置子集**：表内是常见多段后缀（`com.cn` / `co.uk` / `com.au` …）与常见私有后缀（`github.io` / `vercel.app` …）。不在表里的后缀按「单段后缀」处理（取最后两段）求 eTLD+1，最坏表现是「同后缀的两个独立站点被当成一个」：配置与授权合并，但每条规则仍按页面 URL 生效，不会丢用户数据，也不会把样式套到范围外的页面。新增后缀是纯数据改动。
- **已知边界**：IDN 在 punycode 主机名上计算；默认端口（80 / 443）被 URL 规范掉，因此不参与身份；非默认端口不合并子域；`chrome://`、`file://` 等页面本来就不支持。

## 依据

- [Public Suffix List](https://publicsuffix.org/)：eTLD+1 的定义与「公共后缀之下才是注册人可独立控制的域名」。
- [Bitwarden：URI match detection](https://bitwarden.com/help/uri-match-detection/)：默认匹配方式是 Base domain（同一注册域视为同一网站）。
- 1Password 的自动填充文档同样把「网站」定为 eTLD+1（含公共后缀列表），而不是逐个子域精确匹配。
- 浏览器扩展生态的通行做法：权限按 host pattern 授予，但产品层的「网站」按注册域归并，二者用一张映射表衔接——本项目即 `siteKey` / `sitePatterns` / `siteKeyOfPattern` 三个纯函数。
