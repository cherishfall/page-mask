# 管理页拆成独立页面，插件设置注册为 options

0.3.0 的管理页是一个页面、顶部「网站 / 设置」两个 tab。0.4.0 把它拆成**两个独立页面**：网站列表（含点进去的站点设置页，`management.html#/sites`、`#/sites/<域名>`）与插件设置（`settings.html`），面板底部并排两个入口分别进入（#55）。

拆的动因：

- **「设置」的内容变多、且多数与单个网站无关**：默认标题、默认图标（新增的三层中间层）、导出/导入、界面语言、关于——塞在网站列表页的一个 tab 里，每次都要跨页找；独立成页后，改动全局设置的动线与查看网站列表的动线互不打断。
- **Chrome 本来就有「扩展程序选项」这个概念**：插件设置注册成 `options_ui` 且 `open_in_tab: true`，右键工具栏图标点「选项」、或在扩展管理页点「扩展程序选项」，进的就是这一页——顺应平台惯例，用户在 Chrome 的别的入口也能找到它。
- **导出/导入的语义随之变宽**：导出文件从"全部网站配置"变成"全部网站设置 + 插件设置 + 版本号"，放在独立的插件设置页里呈现比藏在网站列表的 tab 里更说得通。

`open_in_tab: true` 是硬要求：Chrome 默认把 options 塞进约 400×600 的小窗，页面布局会全崩。插件设置页左上角有一条返回「你添加的网站」的轻量链接；网站列表页没有反方向的 tab 切换——两页是平级关系，不是主从。

## Considered Options

- **维持两个 tab**：被否决。插件设置的五块内容与网站列表没有共同任务，tab 只增加一次点击；tab 语义还需要 ARIA tab 角色（方向键切换等）的无障碍配套，独立页面用普通链接就够了。
- **三个入口各自独立（网站列表 / 站点设置 / 插件设置都从面板进）**：否决。站点设置没有独立入口的必要——它是从网站列表点进去的下级页面，深链地址保留即可。
- **插件设置注册成 options 但保留 tab**：否决。两个入口进同一个页面的两种形态（tab 与独立页）意味着两套布局与两倍测试面；既然要注册 options，就让它只有一种形态。

## Consequences

- 面板底部是并排的两个入口「管理全部网站」「插件设置」，只占一行高度。
- 站点设置页与插件设置页各有页面标题与返回链接，地址可深链、可前进后退（链接语义，不用 ARIA tab 角色）。
- 右键图标「选项」与面板「插件设置」进的是同一个页面、同一种形态（标签页），不再有小窗版本。
- 导出文件包含插件设置后，导入要分别对账网站配置与插件设置；只有网站配置的旧格式文件仍可导入，不报错。
- `GLOSSARY.md` 的「管理页」「插件设置」词条、`docs/design.md`「界面清单」同步改写；「一键清空」等旧 tab 时代用词一并退役。
