# 幕布控制器唯一：每个文档一个控制器

日期：2026-11-06 · 状态：已采纳 · 相关：ADR-0007（幕布）、ADR-0008（恢复按钮）、ADR-0010（快捷键）

## 背景

幕布有三处入口：胶囊上的「遮住」、弹窗的「遮住这一页 / 恢复这一页」、快捷键（ADR-0010）。0.6.0 装机复核发现组合使用不可靠：未添加过的网站「遮 → 撤 → 再遮」第三次遮不上；两套控制器并存时状态互相矛盾。

根因不是某个按钮，而是**页面上可能同时存在两套幕布控制器**：

- 常规内容脚本有自己的 `CurtainLayer`（`ui/content-runtime.ts`）；
- 一次性脚本（未添加网站）另有 `window.__pagemaskCurtain`（`entrypoints/curtain-oneshot.ts`），它的消息监听只认「查状态 / 撤掉」，**不认「遮住」**——而后台在「没遮着」时发的正是「遮住」；
- 快捷键走「先问状态、再发动作」两步，两步之间状态可能变化；`tabs.sendMessage` 的回复只取第一个，问到可能不是真正遮着的那一层。

## 决定

**每个文档一个幕布控制器**，动作接口固定为 `state() / cover() / dismiss() / toggle()`，`cover` / `dismiss` 幂等；登记在隔离环境 `window.__pagemaskCurtain`（`ui/curtain-controller.ts`），常规内容脚本与一次性脚本共用同一个登记处：

- **后来者的规矩**：一次性脚本见到内容脚本的登记 → 只委托遮住，不铺层、不注册监听；内容脚本见到一次性脚本的登记 → 让位（撤掉它的层、换成自己的登记），之前遮着的话接着遮（遮住状态不丢）。
- **消息只由登记者应答**：两个监听器都动手的话，同一条「切换」会各跑一遍（遮上又立刻切回去），等于没切——这是实现中实测出的坑。应答一律返回**动作执行后**的状态。
- **后台只发一条 `curtainToggle`**：方向由页面控制器决定，不再「先问状态、再发动作」两步；没有接收方才注入一次性脚本。`coverPage` 同理：有接收方（`covered: true`）就让页面控制器遮，不注入第二套。
- **DOM 层硬保证**：扩展重载后的新脚本在另一个隔离环境（实测），看不见旧登记；`CurtainLayer.show()` 铺层前摘掉文档里残留的旧幕布宿主（宿主是本产品自定义元素，页面自己不会长出来），任何时刻文档里最多一个幕布宿主。

## Considered Options

- **保留两套控制器、只补一次性脚本的 `curtainCover` 分支**：否决。两套并存时消息应答谁先谁后不可控，状态仍然可能矛盾；三处入口的互通靠约定而不是结构保证。
- **一次性脚本统一让位 / 内容脚本统一委托**（单一方向）:否决。内容脚本不能委托一次性脚本——它自己的监听还在、消息应答会精神分裂；一次性脚本不能让内容脚本让位——内容脚本持有站点配置与标题守卫，是更完整的控制器。
- **用 chrome.storage 同步两套控制器的状态**：否决。幕布是页面内的临时状态（ADR-0007：不写存储），为它开存储通道违背既有口径，还引入跨上下文的写竞态。
- **消息去重（后台按 tabId 记「上次发给谁」）**：否决。SW 无状态（本架构的既有决定），为幕布引入后台状态不值得；「登记者应答」在页面内部就能把责任分清。

## Consequences

- `core/messages.ts` 新增 `curtainToggle`；`curtainState / curtainCover / curtainDismiss / curtainToggle` 四条消息的语义统一为「作用在登记的控制器上、回复动作后的状态」。
- 内容脚本在**没有站点配置**（站点刚被一键清空）时不占幕布消息的回复通道：它遮不了页，后台会按「没有接收方」注入一次性脚本兜底。这条避免「接收方在、却遮不上」的死状态。
- 向导打开期间页面控制器不铺幕布（进向导前刚撤过，此时的切换请求不应把幕布盖回向导上）。
- 幕布铺开后胶囊仍卸掉（#50 的既有口径不变）：三处入口的「页内恢复」落点是幕布上的「恢复」按钮 + 弹窗 + 快捷键。
- 浏览器级按键无法自动化（ADR-0010 的结论），消息层回归由 `tests/e2e/check-curtain-state.mjs` 覆盖（44 项断言）；真机手测（四组合 + 连按三次）仍需人工执行并记录。
